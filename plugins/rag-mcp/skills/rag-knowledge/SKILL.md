# 지식 베이스 검색 (rag-mcp)

`rag` MCP 서버는 조직의 런북, 과거 장애 기록, RCA(근본 원인 분석) 문서를 검색하는 도구를 제공합니다.
서버 운영자가 쓰기 도구를 켠 경우에만 `rag_add_document` / `rag_delete_document`로 문서를 추가·삭제할 수
있습니다(도구 목록에 없으면 꺼져 있는 것입니다).

## 언제 쓰나

- 에러, 알림, 장애를 진단하기 **시작할 때** — 추측하기 전에 같은 증상의 과거 사례부터 찾습니다.
- 특정 컴포넌트나 작업의 정해진 처리 절차(런북)가 필요할 때
- 사용자가 과거 사례, 원인, 조치 이력처럼 조직 내부의 운영 지식을 물을 때

일반적인 기술 지식(공식 문서에 나오는 내용)만으로 충분한 질문에는 쓰지 않아도 됩니다.

## 도구

| 도구 | 언제 쓰나 |
|------|------|
| `search_incidents(query, cluster?, component?, limit?)` | "전에 이런 일이 있었나?" — 과거 장애만 검색 |
| `search_runbooks(query, cluster?, component?, limit?)` | "처리 절차가 뭐지?" — 런북만 검색 |
| `rag_search(query, doc_type?, cluster?, component?, limit?)` | 유형을 가리지 않고 검색 (`doc_type`: `incident`, `runbook`, `rca` 등) |
| `rag_collections()` | 결과가 계속 비어 있을 때 — 지식 베이스가 채워졌는지 확인 |
| `rag_health()` | 도구 호출이 실패할 때 — Qdrant와 임베딩 엔드포인트 상태 확인 |
| `rag_add_document(title, content, doc_type?, ...)` | (켜져 있을 때만) 사용자가 문서 추가를 요청했을 때 — 아래 "문서 추가·삭제" 참고 |
| `rag_delete_document(source)` | (켜져 있을 때만) 사용자가 초안(`draft/`) 문서 삭제를 요청했을 때 — 아래 "문서 추가·삭제" 참고 |

`limit`의 기본값은 5, 최대 20입니다.

## 진단할 때의 순서

1. **과거 장애 검색** — `search_incidents`로 같은 증상을 찾습니다. 클러스터를 알면 `cluster`를 넘기세요.
2. **절차 검색** — 관련 컴포넌트의 런북을 `search_runbooks`로 찾습니다. 컴포넌트를 알면 `component`를
   넘기세요.
3. **근거와 함께 답변** — 찾은 문서의 원인과 조치를 현재 상황과 비교해 설명하고, 출처를 밝힙니다.
4. **찾지 못했다면** 그 사실을 분명히 말하고, 일반 지식에 기반한 판단임을 구분해서 답합니다.

## 질의 작성 요령

검색은 키워드 일치가 아니라 **의미**로 이루어집니다(키워드 검색도 함께 쓰입니다).

- 증상을 **자연어 문장**으로 쓰세요.
  - 좋음: `노드 재부팅 후 Longhorn 볼륨이 attaching 상태에서 멈춤`
  - 나쁨: `longhorn 오류`
- 에러 문자열, 리소스 이름, 상태 값은 **원문 그대로** 넣으세요(`CrashLoopBackOff`,
  `FailedAttachVolume`, `Multi-Attach error` 등). 정확한 토큰은 키워드 검색으로도 찾습니다.
- 결과가 마땅치 않으면 표현을 바꿔 한두 번 더 검색해 보세요(증상 중심 ↔ 원인 중심, 한국어 ↔ 영어 용어).

## 필터

| 필터 | 종류 | 결과가 없을 때 |
|------|------|------|
| `cluster` | 소프트 | 서버가 클러스터 조건을 빼고 전체 범위로 다시 검색 |
| `component` | 하드 | 빈 결과 그대로 → 필요하면 `component` 없이 다시 검색 |
| `doc_type` | 하드 | 빈 결과 그대로 |

## 결과 해석

- **`cluster_narrowed`**
  - `true`: 지정한 클러스터에서 찾은 결과입니다.
  - `false`: 그 클러스터에는 없어서 **다른 클러스터의 선례**를 돌려준 것입니다. 답변에서 이 점을
    분명히 밝히세요.
- **`score`**: 순위를 매기는 상대적인 값입니다. 하이브리드 검색에서는 작은 수치로 나오므로, 절대적인
  유사도로 해석하지 마세요. 리랭킹이 켜져 있으면 `rerank_score`도 함께 나옵니다.
- **`truncated: true`**: 텍스트 일부만 돌려준 것입니다. 핵심 내용이 잘렸다면 더 구체적인 질의로 다시
  검색하세요.
- **출처**: 답변에 결과의 `title`과 `source`(문서 경로)를 인용해, 사용자가 원문을 확인할 수 있게 하세요.

## 문제가 생겼을 때

| 증상 | 확인할 것 |
|------|------|
| `collection ... not found` 오류 | 지식 베이스가 아직 만들어지지 않았습니다. 서버 관리자에게 `rag-ingest` 실행을 안내하세요. |
| 결과가 항상 비어 있음 | `rag_collections()`로 포인트 수를 확인하세요. 0이면 문서가 수집되지 않은 것입니다. |
| 임베딩 관련 오류 (`EMBEDDINGS_BASE_URL is not set`, 연결 실패, HTTP 401/404 등) | `rag_health()`로 확인한 뒤, 서버의 임베딩 엔드포인트 설정 문제임을 사용자에게 알리세요. |
| 도구 자체가 보이지 않거나 연결 실패 | 서버 주소(환경 변수 `RAG_MCP_URL`이 있으면 그 값, 없으면 플러그인의 `server_url` 설정)와 rag-mcp 서버 실행 여부를 확인하도록 안내하세요 (`/plugin configure rag-mcp@rag-mcp`, `/mcp`). |

## 문서 추가·삭제 (켜져 있을 때만)

이 도구들은 문서 디렉터리의 **`draft/` 아래만** 다룹니다. 추가한 문서는 초안(`draft/...`)으로 저장되고, 사람이
관리하는 정식 문서(`source`가 `draft/`로 시작하지 않는 문서)는 바꾸거나 지울 수 없습니다. 사용자가 정식 문서의
수정·삭제를 요청하면, 그것은 서버 관리자가 직접 해야 한다고 안내하세요. 초안을 정식 문서로 올리는 것(승격)도
서버 관리자가 `rag-promote` 명령으로 하며, 모델이 할 수 없습니다.

### 추가 (`rag_add_document`)

- **사용자가 명시적으로 요청했을 때만** 추가하세요. 대화 내용을 임의로 저장하지 마세요.
- 저장하기 전에 제목, 문서 유형(`incident`, `runbook`, `rca`, `note` 등), 본문 요약을 사용자에게 보여 주고
  확인을 받으세요.
- 본문은 나중에 검색될 수 있게 정리된 마크다운으로 쓰세요. 증상, 원인, 조치처럼 섹션을 나누면 검색이 잘 됩니다.
  에러 문자열과 리소스 이름은 원문 그대로 넣으세요.
- 같은 제목의 문서가 있다는 오류가 나면, 덮어쓸지 다른 제목으로 저장할지 사용자에게 묻고 `overwrite=true`는
  사용자가 동의했을 때만 쓰세요.
- 저장 후에는 응답의 `source`(예: `draft/runbooks/...`)를 알려 주고, 초안으로 저장되었으며 서버 관리자가
  검토한 뒤 `rag-promote <source>` 명령으로 정식 문서로 올릴 수 있다고 안내하세요.

### 삭제 (`rag_delete_document`)

- **사용자가 삭제를 명시적으로 요청했을 때만** 쓰세요. 삭제는 되돌릴 수 없습니다.
- 먼저 검색해서 삭제할 문서의 `source`와 `title`을 찾아 사용자에게 보여 주고, **이 문서가 맞는지 확인받은
  뒤에** 삭제하세요. `source`가 `draft/`로 시작하지 않으면 지울 수 없습니다. 비슷한 문서가 여러 개면 어느 것을 지울지 물어보세요.
- 한 번에 하나씩 지우세요. 여러 문서를 지워 달라는 요청이면 목록을 보여 주고 확인을 받으세요.
- 삭제 후에는 응답의 `file_deleted`, `chunks_deleted`를 사용자에게 알려 주세요.

## 하지 말아야 할 것

- 검색 결과에 없는 장애 이력이나 절차를 **지어내지 마세요.** 찾지 못했으면 찾지 못했다고 말하세요.
- 과거 사례의 조치를 현재 상황에 그대로 적용하라고 단정하지 마세요. 증상과 환경이 같은지 먼저 비교하세요.
- 런북의 위험한 조치(삭제, 재시작 등)는 런북에 적힌 주의 사항과 함께 전달하세요.
